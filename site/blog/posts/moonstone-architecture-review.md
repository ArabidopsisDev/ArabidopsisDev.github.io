黑客松最容易出现两种极端：一种是为了赶时间，把所有代码塞进一个仓库和一个进程；另一种是为了展示“高级架构”，把系统切得过碎，最后大家都在修通信问题。

千知万理选择微服务，因为团队成员的技术栈和交付节奏确实不同。这个选择服务于协作，不服务于架构名词。

## 约束比愿景更真实

比赛开始时，我们面对的是已经存在的能力差异：有人更熟悉 C#，有人使用 Python 处理模型与数据，还有人构建 Web 界面。统一语言的成本高于统一接口，于是架构目标变成了三件事：

- 每个人可以在熟悉的技术栈中独立推进；
- 任意服务的延迟都不阻塞其他成员开发；
- 最终演示时，系统能够被快速启动、观察和解释。

## 先切业务边界，再讨论部署

系统被划分为 API Gateway、核心领域服务、AI/数据服务与基础设施层。边界的判断标准是变化原因：用户流程变化时，核心服务变化；模型或检索策略变化时，AI 服务变化；消息、持久化与外部能力放在基础设施边界。

服务间同步查询使用 REST 或 gRPC，状态变化与非关键链路尽量使用事件传递。这样既能维持演示链路的确定性，也能避免所有模块互相等待。

```text
Client → API Gateway → Core Services
                    ↘ AI / Data Services
Core Services → Events → Support Modules → External Providers
```

## 多技术栈集成，接口就是共同语言

当 C#、Python 和 Web 前端同时存在时，每个人对字段含义的不同理解会直接破坏联调。我们先固定最小契约：请求包含什么、失败如何表达、长任务怎样查询进度、哪些字段可以为空。

契约稳定后，联调从“你那边为什么不工作”变成“这个响应不符合哪一条约定”。沟通方式的变化直接决定了团队能否并行。

### 长任务与失败

模型任务可能持续数十秒。让网关一直等待会占用连接，也会让重试变得危险。因此长任务采用提交、查询和结果读取三个动作：

1. 客户端提交任务并获得任务 ID；
2. 服务通过事件更新任务状态；
3. 客户端查询状态，在完成后读取结果；
4. 相同幂等键不会创建重复任务。

## 队长的工作是保持系统收敛

架构设计之外，还需要确定集成顺序、为卡住的模块提供替代路径、组织系统联调，以及把技术方案翻译成路演语言。答辩也会反过来检验架构：如果几分钟内解释不清问题、边界和数据流，系统设计通常仍然存在含糊之处。

> 队长需要让不同工作最终汇成一个可交付结果。

## 复盘：清晰边界比微服务名词更重要

如果团队只有一个人，或者技术栈完全一致，我不会在黑客松中优先选择微服务。它带来的通信、启动和观察成本都是真实的。在千知万理的约束下，它让不同成员可以并行，也让系统集成有了明确顺序。

比赛结束后，我保留了一条更朴素的经验：先识别真正独立变化的部分，再为它们定义足够小、足够清晰的契约。
