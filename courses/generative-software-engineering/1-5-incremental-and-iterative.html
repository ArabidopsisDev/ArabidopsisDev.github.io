第一章 / 软件过程与过程模型

1.5 增量与迭代

前面几节中，我们已经讨论了复习清单的导出、导入、预览、取消和失败处理，并通过原型比较了替换与合并。如果从还没有文件导入与导出功能的清单开始开发，我们可以等到这些功能全部完成以后，再一起交给使用者；也可以分成几个版本，先让使用者下载进度文件，再增加从文件恢复进度的功能。

假设我们决定分次交付。第一版先支持下载进度文件，使用者可以把清单中三项内容的完成状态保存到电脑上，但还不能把文件读回清单。第二版再增加导入功能，使用者选择文件、查看逐项对照并确认以后，就能恢复文件中的进度。如果使用者后来还需要汇总两台电脑上分别完成的内容，我们再考虑增加合并选项。

像这样分次开发，每次在已有版本上增加一部分功能，就是增量开发。每个版本应当能够完成已经约定的操作。例如，我们已经写好了生成进度文件的函数，但使用者还不能直接在页面上下载文件。我们还要增加“下载进度”按钮，在按钮的点击事件中调用这个函数，再让浏览器下载生成的文件。完成这些代码以后，我们还要点击按钮，核对下载文件中的编号和状态，确认使用者能够通过页面保存进度。

我们先让清单支持下载进度文件，是为了让使用者先把当前进度备份到电脑上。导入功能随后加入，用来读取这些文件并恢复记录。为了实现下载功能，我们需要读取全部条目的状态，按照 1.3 中确定的格式生成 JSON 文件，再通过按钮触发下载。如果使用者手里已经有进度文件，急需把其中的记录恢复到清单，我们也可以先实现导入功能，优先解决他当前遇到的问题。

编写导入代码时，我们可以把工作拆成解析文件、校验内容、显示预览和保存记录等任务，分别实现。但是，前面已经约定，使用者应当先预览，可以取消，错误文件也不能覆盖旧记录。这些步骤共同组成了我们承诺的导入功能，交付时不能拆开。如果先交出一个选中文件就覆盖记录的版本，等以后再补校验和取消，使用者就可能因为选错文件或读到损坏数据而丢失进度。因此，开发者需要把这些步骤都实现好，测试一次完整的导入操作，再把这一版交给使用者。

在交付前，我们可以按使用者的操作顺序测试导入：

  1. 选择一份与本机进度不同的有效文件，查看逐项对照，然后点击取消。页面和刷新后的记录应保持原状。
  2. 重新选择这份文件并确认。页面应采用文件中的进度，刷新以后仍应保留。
  3. 对于文件错误和保存失败，分别按 1.3 中的步骤测试，核对程序是否提示具体原因，并保留旧进度。

如果确认以后还不能保存，这个版本就尚未完成导入功能。我们可以把它作为原型邀请使用者试用，但需要说明当前操作只改变页面内存，刷新后会恢复原来的记录。

在清单已经能够导入文件以后，我们还可能需要继续改进预览。假设试用时，使用者确认导入以后问：“总数还是一项，为什么课堂笔记变成未完成了？”我们需要询问使用者，确认以前认为哪些条目会完成，以了解使用者怎样理解预览。如果使用者已经知道替换会覆盖当前记录，却没有注意到课堂笔记会变回未完成，我们就需要让这项变化更容易被发现。

针对这个困难，我们可以把发生变化的条目放到预览最前面，明确显示“课堂笔记：已完成 → 未完成”，并把确认按钮改为“用文件进度替换当前进度”。修改以后，我们先测试预览、取消和确认是否仍然正常，再邀请使用者尝试同样的任务，听他能否在确认前说出课堂笔记会发生的变化。

如果这轮修改只调整了预览和按钮文字，软件仍然提供原来的替换导入功能，使用者看到的说明则有所改进。我们根据试用时遇到的问题，重新讨论已有功能、修改代码，再测试和邀请试用，这些工作组成了迭代开发中的一轮。一轮迭代也可以增加新功能，例如，我们在改进预览的同时，也可以根据已经讨论清楚的需要增加合并选项。

回看这两个例子，增加导入功能以后，使用者原先只能下载进度文件，现在还能把文件读回清单，我们就交付了一项功能增量。改进预览时，使用者仍然进行原来的替换导入，我们根据试用反馈重新讨论和修改了这个功能，完成了一轮迭代。如果一轮修改既改进了预览，又增加了合并选项，就同时包含了对已有功能的改进和新功能的增加。

改进预览要针对试用中发现的具体困难。如果只让编程助手“再优化一下导入”，它可能换了文字或布局，却没有帮助使用者发现状态变化。对于前面的情况，我们可以这样说明：“使用者理解替换规则，但没有注意到课堂笔记会变回未完成。请把变化条目放到预览前面，并明确显示原状态和导入后的状态。”代码改好以后，我们需要邀请使用者再次尝试，询问确认后课堂笔记会是什么状态。新一轮试用尚未进行时，记录中应写明代码已经修改，使用者能否理解仍待确认。

每次修改以后，我们也要重新操作已有功能。增加导入功能后，要尝试普通勾选、取消勾选和过滤，确认它们仍然正常；改动预览后，要再次点击取消，确认内存中的状态和已经保存的记录都没有变化。我们可以沿用前几节写下的要求和测试步骤，增加新功能对应的操作。如果修改了原先的规则，也要更新相应的预期结果，再运行测试。

第一版下载得到的文件，使用者可能一直保留，等到第二版支持导入时再读取。如果我们编写导入代码时改了编号规则，又没有提供读取旧编号的办法，他原先保存的进度就可能无法恢复。因此，分次实现导出和导入功能时，我们需要沿用 1.3 中确定的文件格式，让后写出的导入代码能够读取先前导出的文件。文件仍然用 formatVersion 标明格式版本，用 progress 中的 id 和 completed 记录各项进度。

为了测试新版本能否读取旧文件，我们需要保留一份第一版实际生成的文件。第二版写好以后，我们就用这份文件尝试导入，再核对恢复出的状态。如果测试时只按新代码的规则临时写了一份样本，就可能遗漏新旧版本之间的不一致。以后确实需要改变文件格式时，我们还要说明怎样识别旧格式，并提供相应的读取、转换办法，或者明确告诉使用者哪些文件暂时不支持。

网页更新与文件格式改变也需要分别处理。假设我们只改了按钮文字和预览顺序，文件中的字段及其含义都没有变化，那么新页面仍然可以按原来的规则读取 formatVersion: 1 的文件，格式版本号也无需改变。如果以后把 completed 换成其他字段名，旧文件与新文件就需要按不同规则读取，我们才需要相应的版本识别和兼容处理。

修改代码以前，我们也需要考虑出错后怎样恢复。Git 可以保留上一版代码，但如果新版程序已经把错误进度写入浏览器，切回旧代码以后，那份错误数据仍然存在。恢复代码不会自动恢复被覆盖的进度。因此，修改导入规则或数据结构以前，我们还要另存一份进度备份，保留能够恢复数据的办法。

交付每个版本以前，我们都需要运行约定的操作，核对实际结果。例如，测试下载功能时，要点击页面上的按钮，并打开下载文件，核对三个编号和完成状态。测试导入功能时，则需要用上一版导出的文件完成预览和确认，刷新页面后核对恢复出的状态。记录开发进度时，也需要区分代码已经写完、测试已经通过和版本已经交给使用者这几种情况，以免把尚未验证的代码当作已经完成的功能。

接下来，你可以在自己的清单上实践这些做法，也可以下载起始项目、文件样本和提示词。起始页面已经支持勾选、保存、过滤和数量显示，还没有导出与导入功能。如果你已经完成了 1.3 的实践，就可以保留已有功能，用之前导出的文件测试兼容性，再根据实际试用中遇到的困难改进预览。

如果使用者后续确实需要合并进度，你可以先与他讨论 1.4 中的规则是否适用：同一编号在任意一边已经完成，合并后就保留为已完成；两边都未完成时，结果为未完成。确定规则以后，再让编程助手增加合并选项，仍然先预览、确认后保存。你还需要重新尝试原有的替换方式，确认它没有受到影响。由于文件已经记录了编号和完成状态，程序可以沿用原格式读取数据，再根据所选规则计算合并结果。

完成实践以后，你可以对照代码和记录回看：哪个版本增加了下载功能，哪个版本增加了导入功能？如果你还改进了预览，是使用者遇到了什么困难，你怎样修改，又怎样了解修改后的效果？对于尚未完成的测试或试用，你也要记下来，方便以后继续。

复习与思考

  1. 开发者可以分别编写解析文件、校验、预览和保存代码，但按照本例的要求，为什么不能先交付一个缺少校验或取消操作的版本，把这些部分留到以后再补？你会怎样区分编写任务与完整的导入功能？
  2. 增加导入、修改预览文字、增加合并，分别新增或改善了什么？为什么一轮修改可能同时包含增量和迭代？
  3. 如果程序还没有拒绝带有未知编号的文件，能否先发布导入功能，再到下一版补上？你会根据哪些已经确定的要求作出判断？
  4. 为什么测试第二版的导入功能时，要使用第一版实际下载的文件？只用本轮新写的样本可能漏掉什么？
  5. 调整按钮文字以后，是否需要修改文件格式版本？如果真的改了字段结构，又要考虑什么？
  6. 回退到上一版代码后，浏览器里的完成记录会自动恢复吗？涉及错误导入时，你需要另外准备什么？
