# 开发工作看板

团队通过卡片记录开发工作当前处于什么状态。
本项目初始时有两项工作进行中：上传提示在待验证并标记受阻，导入确认按钮在开发中。
日期文件名和上传前查看进度变化保留在待开始。

## 运行

在解压后的目录打开终端，运行：

```sh
python -m http.server 8092
```

浏览器访问 http://localhost:8092/ 。
如果端口已经被占用，可以改用其他空闲端口。
JavaScript 模块需要通过 HTTP 打开。

卡片和操作记录保存在当前页面内存中，刷新会恢复案例起点。
页面按钮只改变卡片记录。实际项目的代码修改与测试，需要在业务项目中执行。

## 进行中工作

开发中与待验证共同计数，受阻卡片也保留在原列并继续计数。
初始上限为 2，可以在页面上选择 3 或 4。
如果当前已有 3 项进行中，改成上限 2 会被拒绝，卡片的实际状态保持原状。

1. 保持案例起点和上限 2，尝试开始日期文件名，页面应提示已经达到上限。
2. 把导入确认按钮移到待验证，再尝试开始日期文件名。进行中总数仍为 2。
3. 在当前推演中解除上传提示的阻碍，查看本项完成条件，勾选确认后移到已完成。
4. 此时进行中总数降为 1，可以开始日期文件名。
5. 将待验证卡片返回开发，数量保持不变。你也可以填写原因并标记受阻，观察卡片继续计数。

完成条件需要逐项核对。实际协作中，解除阻碍需要依据缺少的条件已经得到满足。
移动卡片的操作记录只能说明页面操作，真实开发时间需要另行记录。

## 配套记录

在 workflow.md 中约定工作状态、开始与完成条件，以及如何控制进行中数量。
在 run-notes.md 中记录页面实际运行结果，未运行的部分保留为待执行。
在实际项目中使用这些约定以后，填写 flow-record.csv。
根据实际开始与完成时间整理历时，包含中间等待的时间。
review.md 用于记录等待原因和准备改变的协作安排。

服务水平预期需要写明时间范围与可能性，并记录依据。
缺少历史数据时，可以与成员讨论初始估计，后续根据实际记录调整。
页面点击间隔反映的是操作过程，实际软件开发历时采用业务项目中的时间记录。

prompts.txt 与课程页面保留相同的三段提示词。

## 代码

board-core.js 保存卡片与上限，根据操作返回新状态。
它在开始或重新打开工作时核对名额，并在完成以前要求确认完成条件。
board.js 显示这些状态，并将按钮操作交给 board-core.js。
