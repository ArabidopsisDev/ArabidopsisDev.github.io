# 手动上传与使用反馈

复习清单记录本机的完成状态。
使用者勾选“课堂笔记”以后，还需要点击“上传本机修改”，共享记录才会保存这项状态。
另一台设备随后读取共享记录，才能看到课堂笔记已完成。

## 运行

在解压后的目录打开终端，运行：

```sh
python -m http.server 8091
```

浏览器访问 http://localhost:8091/ 。
如果该端口已经被占用，可改用其他空闲端口。
脚本采用 JavaScript 模块，需要通过 HTTP 打开页面。

实验数据保存在当前页面内存中，刷新后恢复初始状态。
页面函数执行上传与读取。真实服务中的网络请求和持久保存，需要在原项目中另外验证。

## 正常上传

初始时三项内容均未完成，共享记录为第 7 版。
每次接受修改以后，共享记录的版本号就加 1。

1. 保持提示关闭，勾选本机“课堂笔记”。本机这项内容已完成，共享记录中应当未完成。
2. 展开共享记录核对，再打开提示。页面应说明本机修改尚未上传。
3. 点击“上传本机修改”。共享记录中课堂笔记应改为完成，版本成为 8。提示应显示本机当前进度已上传。

“显示上传状态提示”只控制提示是否显示，本机与共享记录仍按原来的规则更新。

## 提交被拒绝

恢复初始状态，在本机勾选“矿物识别”。
点击“模拟手机上传练习题进度”以后，共享记录成为第 8 版。
随后点击“上传本机修改”。本机仍依据第 7 版提交，因此这次提交应被拒绝。

本机需要保留“矿物识别”已完成的状态。
共享记录中“矿物识别”应未完成，“练习题”应已完成。
打开提示以后，页面应说明本机修改已经保留、尚未上传。

本机有待上传修改时，读取会停止，以保留本机数据。
当前项目尚未实现冲突合并，可以在自己的项目中继续补充。

提示中的版本号表示本机上次读取或成功上传的那份记录。
其他设备后来还可能继续上传，因此这条提示只能说明本机已经取得的结果。

## 试用记录

邀请使用者尝试时，可以在上传前后分别问：
“现在另一台设备读取，课堂笔记会显示已完成，还是未完成？”

尚未上传时，预期回答是未完成。
上传成功后，预期回答是已完成。
等使用者回答以后再解释原因，并保留使用者的原话。

feedback.md 记录两次回答及对操作是否方便的讨论。
你可以据此在 improvement-plan.md 中提出修改内容。
代码改好以后，运行 checks.md 中的步骤，填写实际结果。
再次试用以后，在 reflection.md 中记录准备继续修改提示，还是讨论自动同步。

没有邀请他人时，使用者的试用保留为待执行。
prompts.txt 保存与课程页面一致的三段提示词。

## 代码

state-core.js 根据操作返回新的实验状态，lab.js 把这些状态显示到页面。
判断本机是否有待上传修改时，程序比较当前进度与上次读取或上传后的基准进度。
另一台设备更新共享记录以后，本机仍保留上次读到的版本号。
上传时，如果这个号码与共享记录的版本不同，就拒绝保存，并保留本机修改。
