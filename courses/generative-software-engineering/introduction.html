绪论

为什么还要学软件工程？

我写过一个叫 AquaAvgFramework 的框架，用来制作和播放视觉小说。这类游戏通过背景、人物立绘和文字来讲述故事。“立绘”就是显示在画面中的人物图片。玩家点击后可以继续阅读下一句台词，遇到选项时可以作出选择，不同选择可能通向不同的后续情节。游戏还可以播放背景音乐，让人物通过动画出现或离开。

Aqua 负责把这些内容显示出来：人物立绘显示在背景上面，人物的名字和台词显示在对话框里；玩家点击后，播放器继续显示下一句台词，遇到剧情分支时则显示选项。Aqua 使用 WPF 开发。WPF 是用于开发 Windows 桌面界面的技术，提供文字、图片和按钮等组件，Aqua 用这些组件实现视觉小说的播放功能。

我还写过一款帮助用户学习和复习的软件，叫 ReciteHelper。当时，我想让用户在阅读故事的过程中复习知识：把学习资料里的知识点写进剧情，让人物通过对话讲解、讨论这些知识，用户则通过阅读和选择完成复习。旧版生成提示词中还明确要求把复习内容融入恋爱故事。

要实现这个功能，我需要先根据学习资料生成故事，再把故事显示成上面那样的画面。ReciteHelper 已经能够处理学习资料、调用模型，而 Aqua 已经能显示人物、播放对话并处理选项。我当时希望把 Aqua 接入 ReciteHelper，由它负责显示人物、播放对话和处理选项。复用这些功能，可以减少重新编写播放器所需的工作。

我当时所说的移植，就是把 Aqua 接入 ReciteHelper，让它负责播放生成的故事。两者都使用 WPF，所以最初看来，这样做很合适。后来，随着功能增加，我把 ReciteHelper 的代码拆分到了多个项目中，希望处理故事内容的代码与显示窗口的代码能够分开。这时，我才需要仔细检查：Aqua 里的故事处理代码能否单独使用？如果拿走这部分代码，是否必须把原来的窗口组件也一起带过来？

在 WPF 中，用来显示文字、图片，或者接收用户操作的界面组件通常称为控件。Aqua 的整个播放面板是一个控件，画面下方的对话框也是一个控件。对话框放在播放面板内部，由面板中的布局区域安排它的显示位置。

代码中的 GamePanel 对应整个播放面板，CenterGrid 是面板里用来放置对话框的布局区域，CenterBubble 则是实际显示名字和台词的对话框。程序创建对话框以后，还需要把它加入布局区域，才能在面板中显示出来。

那么，播放器怎样知道下一句要显示什么？Aqua 用 PlainDialogue 对象保存一次普通对话，其中包括人物名字和台词。我们先把它称为对话对象。对话对象与屏幕上看到的对话框是两个不同的对象。前者保存内容，还包含将内容显示出来的方法；后者是调用这个方法时创建的界面控件。

播放到这句对话时，程序会调用对话对象的 Enter 方法。这个方法取出保存的“林同学”和台词，创建对话框，再把它加入播放面板的布局区域。完成这些操作以后，玩家才能在画面中看到这句对话。

从这几行代码可以看出，对话对象除了保存名字和台词，还要创建 Aqua 的对话框，并把它放进播放面板。它使用的字体、布局和动画类型也来自 WPF。如果我们把对话对象的代码复制到另一个项目，就必须同时提供这些类型，否则代码无法通过编译。这就是这里所说的与界面绑定。

创建对话对象时，程序可以先把名字和台词保存在内存中；调用显示方法时，才会创建对话框并将它加入播放面板。编译这段代码的项目需要引用相应的界面框架，才能找到对话框、字体和布局等类型。如果我们希望在没有这些界面类型的项目中处理故事，就需要重新分配内容保存与界面显示的工作，调整相关类型引用和方法调用。

一段故事通常包含多句对话，还可能需要更换背景、显示选项或跳到另一段剧情。Aqua 用 StoryLine 组织这些内容，可以先把它理解为按播放顺序排列的一组故事元素。播放面板从中取出下一项，再调用这一项的方法，完成显示台词或更换背景等操作。

随着 ReciteHelper 的功能增多，我把代码拆到了不同的项目中：显示窗口的代码放在一处，安排功能执行步骤的代码放在一处，核心规则和文件读写等具体实现也分别存放。这就是这里提到的分层，每一层负责一部分工作。

拆分以后，我希望可以单独检查台词、调整故事生成方式，把窗口组件的操作留给播放器。因此，我需要查看处理故事内容的代码，找出其中对对话框、播放面板等界面类型的引用。

如果一段代码需要使用另一个类型，或者调用另一个模块提供的功能，我们就说它依赖这个类型或模块。前面的对话对象需要创建对话框、调用播放面板中的布局操作，因此依赖它们。拆成不同项目以后，对话对象如果继续创建对话框、调用播放面板，它仍然依赖这些界面类型。

当时，我还增加了一个服务接口 IGalGameService，让其他代码通过它调用故事编译、读取和保存等功能。接口声明了可以调用哪些方法，具体怎样编译、怎样读写文件，则由实现这个接口的代码负责。

其中，读取故事的方法返回一组 object。在 C# 中，object 可以用来接收多种类型的对象。调用者需要继续查看读取方法的实现，才能知道具体返回哪种故事对象。返回值写成 object 时，程序实际创建的对象仍然保留自己的类型。

剧情窗口加载故事后，会把这些对象按 Aqua 的故事线类型整理成列表，再交给播放面板：

GamePanel.StoryLines = storyLines.Cast<StoryLine>().ToList();

右边的 storyLines 是读取服务返回的一组对象。Cast<StoryLine>() 要求把其中每个对象按 Aqua 的“故事线”类型使用；如果实际对象不符合这个类型，就会出错。

ToList() 把转换后的结果整理成列表。等号左边的 GamePanel.StoryLines，表示播放面板要播放的故事线列表。这行代码最终把读取结果交给了界面中的播放器。

可以看到，读取服务仍然按 Aqua 的类型创建故事对象，窗口也仍然按这些类型使用它们。读取和显示这两部分代码通过 Aqua 的故事对象交换数据。要把故事内容与播放器分开，还需要改变传递的数据以及两边使用它的方式。

这里也需要注意，分层之后，负责界面的项目仍然可以使用 WPF。删除剧情功能前，负责具体实现的项目也仍然面向 Windows，并引用了 Aqua。当时我希望改变的是故事处理与界面之间的关系。整个软件对 Windows 的依赖，还需要结合各个项目的目标平台、引用和实际调用来判断。

因此，能不能继续复用 Aqua，要看我希望复用哪些功能。如果目标是在原来的 Windows 窗口中播放剧情，可以继续接入它的播放器。如果还希望单独处理故事内容，避免依赖界面框架，就需要修改现有代码，把台词、选项等内容与窗口显示分开。

ReciteHelper 的提交记录保留了剧情功能从接入、调整到删除的过程。

2026 年 1 月 6 日，提交 0bf6bb3 开始接入 Aqua，增加 GalGame 项目类型、剧情窗口和故事编译入口。这里的编译入口，会执行生成出来的 C# 故事代码，得到框架能够使用的故事对象。

2 月 25 日，提交 51705d2 将 Aqua 加为 Git 子模块，并调整项目引用。子模块是在当前仓库中记录另一个仓库的位置与版本，让其他开发者获取代码时也能找到依赖。它帮助获取框架代码，没有改变故事对象怎样操作窗口。

6 月 8 日，提交 fe1516c 继续拆分和整理项目，窗口与资源进入 Wpf，相关工具进入 Infrastructure。6 月 14 日的 4d66dc9 又增加故事创建与保存等服务。前面看到的接口整理，正属于这段调整过程。

10 月 9 日，提交 3943f38 删除了剧情服务及接口、故事编译方法、创建与播放窗口、菜单入口、提示词和相关资源，同时移除 Aqua 子模块及项目引用。至此，生成、保存和播放剧情的相关功能都被移除了。

从代码和自己的开发经历来看，Aqua 将故事对象与界面绑定在一起，不适合我后来希望实现的分工。这些提交记录呈现了接入、调整和删除的过程。要判断跨平台运行情况，还需要另外进行运行实验。这里要解决的是 Aqua 在新项目结构中的复用问题，它原有的 WPF 播放功能仍然可以使用。

如果要继续保留剧情复习功能，我们可以先列出用户会进行的操作：阅读故事、查看对话，以及在分支处作出选择。这些操作都需要播放器显示内容。至于名字、台词和选项，可以由其他代码负责保存，再交给播放器。我们可以按照这样的分工调整现有代码。

例如，可以把人物名字和台词单独保存成数据，播放时再交给播放器：

{
  "speaker": "林同学",
  "text": "昨天那块岩石，为什么会有一层层的纹路？"
}

上面的数据使用 JSON 格式，speaker 保存说话者的名字，text 保存台词。名字和台词先作为文字保存，字体和对话框由播放器在读取后设置。

这样修改以后，故事对象负责保存内容，播放器负责创建界面控件。以后调整台词格式或增加检查规则时，就可以主要修改内容处理代码，减少对界面代码的改动。

要完成这样的改造，还需要确定怎样记录选项跳转、音乐和动画，以及是否继续读取旧版故事文件。修改后也需要实际运行，检查台词顺序、选项结果和播放效果是否正确。前面的数据格式只说明了台词可以怎样保存，其他问题还需要逐一处理。

如果改造成本太高，也可以保留原来的桌面播放方式，或者暂时移除剧情功能，先完善其他学习与复习功能。作出选择时，需要考虑这个功能对用户有多大帮助、修改需要多少工作，以及以后怎样维护。即使已经有很多现成代码，也仍然需要考虑这些问题。

那么，AI 已经能生成代码，为什么还需要学习软件工程？在当时的剧情功能中，ReciteHelper 已经会调用模型，把复习内容交给它，生成用于创建 Aqua 故事对象的 C# 代码。程序执行这些代码，得到故事对象，保存后再交给窗口播放。

如果模型继续生成创建 Aqua 对象的代码，后面的程序就仍然需要引用 Aqua 的类型。如果改成让模型生成前面的 JSON 数据，我们还需要确定完整的数据格式，检查台词、选项和跳转关系，再编写播放器读取数据的代码。我们需要让提示词生成的数据与程序读取的格式一致，同时修改故事生成、校验和播放代码。

编程 Agent 是能够使用工具读取和修改代码、运行命令的 AI 开发助手。即使把移植工作交给它，我们也需要说明自己的要求：是否继续使用现有窗口播放故事？是否需要在不开窗口时检查故事？旧文件是否还要继续读取？哪些代码可以修改？修改后怎样检查原有的复习功能？

如果这些要求没有说清楚，Agent 可能会选择继续使用 Aqua 原有的窗口和故事对象。这样或许能够播放剧情，却没有满足把内容处理与界面分开的要求。检查它的修改时，我们需要沿着对象的创建和传递过程阅读代码，找到内容处理部分仍在使用的界面类型，再尝试在预期的项目中编译和运行。这样才能核对依赖关系是否符合要求。

处理这些问题时，我们会用到软件工程中的需求分析、代码组织、测试和版本管理。需求分析帮助我们确认为什么要接入这个功能、希望它怎样工作；阅读代码中的依赖，可以判断哪些部分能够复用；测试用于检查修改后的行为；版本管理则让我们保留修改记录，并在需要时恢复旧版本。这些工作也决定了我们该让 AI 做什么，以及怎样检查它的结果。

例如，你希望单独检查台词，却发现对话对象中还使用了 WPF 的字体、对话框和布局操作，就需要考虑怎样去掉这些依赖。如果你只需要在现有 WPF 窗口中播放，则可以保留原来的做法。AI 可以帮助修改代码，但我们仍然需要根据软件要完成的任务，判断该修改哪些关系，并检查结果是否符合要求。

复习与思考

  1. 我希望通过移植 Aqua 为 ReciteHelper 增加什么功能？为什么最初会认为直接复用播放器比较合适？
  2. 对话对象中除了名字和台词，还依赖了哪些界面类型和操作？为什么把接口返回类型改为 object 没有消除这些依赖？
  3. 继续在 WPF 窗口里播放故事，以及在没有窗口组件的项目中处理故事，这两个目标分别需要考虑哪些改动？交给 AI 以前，你会怎样说明自己的要求？
