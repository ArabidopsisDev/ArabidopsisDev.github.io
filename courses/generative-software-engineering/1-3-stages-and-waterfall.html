第一章 / 软件过程与过程模型

1.3 将工作划分为阶段

复习清单现在可以保存完成状态，隐藏已完成项，并显示还有多少项待复习。假设使用者在家里的电脑上完成了一部分复习，接着换到另一台电脑打开清单，却发现三项内容仍然都是未完成。原来的记录保存在家里那台电脑的浏览器中，新电脑无法直接读取，所以没有恢复出原来的进度。

为了解决这个问题，我们准备增加导出和导入功能：使用者在原电脑上把复习进度保存成文件，再把文件带到另一台电脑，让清单读取。两台电脑中的条目标题、来源和编号相同，需要迁移的是每项内容的完成状态。因此，文件需要保留条目编号，让程序知道每条状态属于哪项内容。

文件中的进度可能与本机已经保存的进度不同。编写导入按钮和读写代码以前，我们需要先确定程序应该怎样处理这种情况，以及选错文件或操作失败时怎样保留原记录：

  1. 另一台电脑如果已经有复习记录，导入文件后，是替换这些状态，还是把两边的已完成项合并？
  2. 使用者选中文件以后，程序是在这时修改记录，还是等待确认后再修改？如果选错了，在哪里取消？
  3. 文件损坏、编号不匹配，或者浏览器保存失败时，原来的记录会怎样？
  4. 导入完成以后，待复习数量和当前过滤结果应当在什么时候更新？

这些决定会影响导入时的行为。首先看第一条：如果使用替换策略，程序就用文件中的完成状态覆盖本机原有状态；如果使用合并策略，就需要进一步规定两边状态不一致时怎样处理。例如，本机已经完成、文件中却未完成的一项内容，合并后应该保留哪一个状态？

对于第二条，如果允许取消，程序就需要在读取文件后，先把待导入的数据保留在内存中，让使用者查看哪些记录会发生变化。使用者确认以后再保存；如果取消，就放弃这份待导入数据，保留本机原来的进度。

第三条包含两种不同的失败。文件损坏或编号不匹配时，程序应当在覆盖原记录以前完成校验，并提示具体问题。例如，文件缺少第三项记录，就不能继续导入，否则这项内容的完成状态没有依据。

浏览器保存失败，则发生在文件已经通过校验、使用者也已经确认之后。此时程序还没有成功保存新进度，需要提示保存失败，并继续显示原来的状态，避免页面看起来已经导入成功，刷新后却又恢复旧记录。

最后看第四条，导入成功以后，复选框、待复习数量和过滤结果都需要按新状态更新。例如，假如只有第三项从未完成变成已完成，那么待复习数量应减少一项；如果打开了“只看未完成”，这一项也应从当前列表中隐藏。

为了确定软件应当提供哪些操作，我们讨论了导入后的完成状态，以及取消或失败时如何保留原记录。这些要求会成为后续工作的依据：我们需要据此选择文件格式和处理步骤，编写相应代码，并用实际操作核对结果。按照这些工作的目的，可以将开发划分为需求、设计、实现和测试等阶段。

我们目前要实现的是恢复一份已经保存的进度，让本机的三项状态与文件一致。因此，我们决定采用替换策略：使用者确认导入后，用文件中的完成状态覆盖本机原有状态。在确认以前，页面先逐项显示本机状态和文件状态，让使用者看清导入以后每一项会变成什么状态；使用者也可以取消，保留本机进度。

我们刚才确定了软件应该怎样处理进度，这属于需求分析与定义。我们还要检查这些要求是否符合迁移目的、是否有遗漏。例如，使用者需要在新电脑上接着复习，就必须知道具体完成了哪几项。只导出“已完成两项”这个总数，无法恢复每一项的状态。

明确这些行为以后，我们开始设计文件结构和处理步骤。JSON 可以把条目编号和完成状态写成带有字段名的数据。我们用 id 保存编号，用 completed 保存完成状态，程序读取以后，就能按编号找到对应条目。

确定格式时，还需要考虑用户可能保留旧文件。如果以后把 completed 改成其他字段名，或者改用另一种方式表示完成状态，导入程序就需要知道这份文件按哪套规则读取。为此，我们在文件中增加了 formatVersion，用它标明文件格式的版本。当前使用的格式记为数字 1，程序读到这个版本后，就按下面的字段结构处理：

{
  "formatVersion": 1,
  "progress": [
    { "id": "r001", "completed": true },
    { "id": "r002", "completed": false },
    { "id": "r003", "completed": true }
  ]
}

文件中的 progress 是一组进度记录。每条记录用 id 标识复习内容，用 completed 保存完成状态：true 表示已完成，false 表示未完成。上面的数据表示课堂笔记和练习题已完成，矿物识别尚未完成。如果程序读到尚未支持的格式版本，应当提示无法读取；要支持新版本，还需要编写对应的读取或转换代码。

由于清单包含固定的三项内容，导出文件需要包含 r001、r002 和 r003 的完成状态。导入时，程序要检查这三个编号是否齐全、是否重复，以及有没有不属于当前清单的编号。每个编号应当对应一条记录，否则程序无法确定这个条目最终应该采用哪一个状态。

程序还需要检查字段类型。例如，false 是布尔值，而 "false" 是一段文字，程序需要区分这两种类型。文件如果使用了错误的类型，应当提示错误，交给使用者处理以后再导入。

导出要保存整个清单的进度。打开“只看未完成”后，页面会隐藏已完成项，完整清单仍然保留它们的数据。因此，生成文件时需要读取完整清单，把隐藏条目的状态也写进去，这样才能在另一台电脑上恢复全部进度。

按照图中的步骤，程序先读取并检查整份数据，再让使用者确认，最后才保存。假如程序改成每读到一项就保存这一项，那么前两项可能已经覆盖了旧进度，读到第三项时才发现它的编号重复。导入虽然报错，原记录却已经改动了一部分。把待导入数据与当前进度分开，完成全部校验以后再保存，可以避免这种情况。

文件格式和处理步骤明确以后，我们根据方案编写导出、文件读取、校验、预览和保存代码，这部分工作属于实现。编写代码的同时，也可以逐个检查其中的函数。

例如，我们可以把文件格式检查写成 validateProgress(data)。文件读取代码先把 JSON 解析成数据，再传给这个函数。函数负责检查版本、编号和完成状态，返回检查结果；文件读取、界面显示和本地保存由其他代码负责。

对于有效数据，我们要求函数返回“通过”以及三条经过检查的进度记录；对于重复编号、缺少记录等无效数据，要求它返回“未通过”和具体原因。这样，就可以准备几组输入，单独调用这个函数，再将返回结果与预期比较：

进行这些检查时，我们直接把准备好的数据传给函数，再比较返回结果。文件选择、预览和确认由其他代码负责，可以在检查完整导入流程时另外操作。把一个函数或一小段程序作为检查对象，并用给定输入核对结果，就是这里的单元测试。测试代码可以自动完成这些调用与比较，发现返回结果不符合预期时，就报告失败。

单元测试通过以后，我们还需要进行集成与系统测试。集成测试关注各部分接在一起以后能否配合，例如，校验函数返回错误后，页面是否停止导入并显示原因。系统测试则从完整软件的使用过程出发，核对功能要求。对于进度迁移，我们可以这样测试：

  1. 在原清单中准备一组进度，下载文件，然后在存储相互独立的另一份清单中选择这个文件。确认以前，预览应逐项显示本机状态和文件状态。
  2. 点击取消，核对本机进度是否保持原状。重新选择文件并确认后，核对清单是否采用了文件中的状态；刷新页面以后，这些状态应当仍然保留。
  3. 分别选择损坏或内容不符合要求的文件。程序应说明错误，原进度应保持不变。保存失败发生在确认以后，需要另设一次测试，核对失败提示和原进度。
  4. 在上述操作后查看待复习数量，并切换“只看未完成”，核对它们是否与当前完成状态一致。

把功能交给使用者以后，我们还需要了解使用者在实际设备上能否顺利操作。例如，使用者能否找到刚导出的文件，能否在另一台电脑上导入，以及是否知道确认以后哪些记录会被覆盖。如果使用中出现问题，我们就需要根据操作记录排查原因，修复后测试受影响的功能，再提供更新版本。这些工作属于运行与维护。以后增加条目或调整文件结构时，我们还要用使用者已经保存的旧文件测试导入，确认它们仍然可以读取。

如果按照上面的安排开发，需求、设计、实现与单元测试、集成与系统测试、运行与维护，就构成了前后相接的阶段。瀑布模型强调这种阶段顺序：每个阶段集中完成一类工作，对照要求核对这一阶段的结果，再把结果交给后续阶段使用。

划分阶段以后，每个阶段仍有需要核对的结果。例如，需求分析与定义阶段应当说明导入是替换还是合并，以及使用者何时可以取消。如果这些要求有遗漏，后续方案就可能采用错误的处理规则。在实现与单元测试阶段，我们要根据设计编写代码，并通过给定输入核对函数的返回结果。到了集成与系统测试阶段，才能进一步核对这些代码接在一起以后，完整操作是否符合要求。

如果导出和导入由两位开发者分别编写，他们需要使用同一份格式说明。导出方按照说明写入三个编号和布尔状态，导入方按照相同规则读取和校验，双方才能配合。负责测试的人也可以据此准备输入和预期结果。如果开发暂停几周后再继续，我们也能查到当时确定的替换规则和保存顺序。

准备进入下一阶段时，我们需要审阅前一阶段的结果，判断它是否足以支持接下来的工作。例如，需求文件没有说明替换还是合并，设计时就无法确定两边状态不同应当怎样处理。保存失败后的行为如果没有确定，实现代码时也就缺少失败处理的依据。遇到这些遗漏，需要回到相应的需求或设计中补充，后续代码才能按照确定的规则实现。

准备进入的工作需要先确认什么如果没有确认
设计文件和导入步骤导入替换还是合并？确认前能否取消？可能按错误的行为编写后续方案
实现导出和导入字段、版本、编号规则与失败处理是否明确？不同部分可能无法配合，错误文件也可能改动旧数据
交给使用者正常导入、取消、错误文件和原有功能是否已检查？按钮虽然能操作，实际记录仍可能不正确

要求也可能在使用过程中改变。假设使用者最初只想恢复原电脑导出的那份进度，后来开始交替使用两台电脑，两边都产生了新记录，于是希望保留两边已经完成的内容。这时，我们需要与他讨论合并规则，再调整预览和保存前的数据处理，修改相应的测试用例并重新运行。原来的替换功能仍然可以使用，但它无法把两边已经完成的内容合到一起。

另一种情况是，使用者从一开始就在两台电脑上复习，但我们讨论需求时没有问清楚，却一直按替换策略编写代码。直到使用者实际操作，我们才发现，使用者原本希望保留两边已经完成的记录。此时，我们就要回头修改已经写好的方案、代码和测试。为了更早发现这种误解，我们可以请使用者尝试导入预览，并在确认前说明自己想保留哪些记录。如果预览结果与这个需要不同，就应当讨论处理规则，再继续编写依赖这些规则的代码。

瀑布式安排更容易用于主要要求已经清楚、后续变化较少的工作。例如，导入文件的字段和含义已经确定，使用者也确认了替换规则，我们就可以据此安排设计、实现和检查。如果替换还是合并仍有争议，我们就需要先讨论或试用，确定希望保留哪些进度，再据此安排后续方案和代码。

阶段中的检查如果发现遗漏，也需要回到相关工作进行修改。例如，系统测试发现旧文件无法读取，就要重新检查格式要求和读取方案，并更新受影响的代码与测试。Royce 在 1970 年关于大型软件开发的讨论也指出了关键问题留到后期才被发现的风险，并提出早期试做、持续让客户参与检查等做法。

  2. 启用一个可以撤销的临时故障，让下一次保存报告失败。选择有效文件，完成校验并点击确认。
  3. 程序应提示保存失败，页面仍应显示三项未完成。刷新后，这组状态也应保持不变。
  4. 移除临时故障，再次选择同一个文件并确认。保存成功后，页面和刷新后的记录应与文件一致。

检查文件迁移时，可以把项目放到另一台电脑上运行。也可以先在两个终端中分别执行 python -m http.server 8000 和 python -m http.server 8001，通过两个端口访问同一项目。浏览器会分别保存这两个地址的记录，因此可以在一边导出、另一边导入，核对迁移结果。同一地址下的两个标签页会共用本地存储，不能用来完成这项检查。之后仍需要在实际使用的另一台设备上确认操作是否正常。

复习与思考

  1. “支持导入导出”为什么还不足以指导实现？请从替换或合并、确认或取消、失败处理三个方面补充要求。
  2. 导入会替换当前状态，与使用 JSON 保存版本和编号，分别属于哪一类决定？为什么需要先确定前者，再完成后者的方案？
  3. 为什么需求文件写完了，需求阶段仍可能没有完成？你会检查哪些内容，判断它能否供后续设计使用？
  4. 如果直到完成实现后，使用者才要求把替换改为合并，哪些阶段的结果需要重新检查？为什么仅修改一个判断条件可能不够？
  5. 把系统测试安排在实现之后，是否意味着前面不需要检查？请分别举出需求、设计和实现阶段能够提前检查的问题。
  6. 假如使用者还看不懂导入预览，你会继续完善所有导入代码，还是先让对方操作一个预览界面？你希望通过这次操作确认什么？

接下来，我们会先做出可以操作的导入界面，请使用者尝试替换和合并，了解他怎样理解这两种操作，以及能否看出每一项的状态变化。
