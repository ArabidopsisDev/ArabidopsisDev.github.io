第一章 / 软件过程与过程模型

1.1 什么是软件过程

假设我们正在开发一个复习清单，用来记录每天要复习的内容。我们已经做出了一个网页，能把“复习岩石分类”“复习矿物识别”等条目列出来，但还不能记录复习进度。复习中途离开一会儿，再回来时，我们就可能忘记哪些已经完成。因此，我们准备在每项内容旁边加一个复选框：复习完一项，就勾选一项，让程序保存完成状态，方便下次接着复习。

如果让 AI 帮忙实现，我们可能会告诉它：“给每一项加一个复选框，勾选后显示删除线。”这条要求说明了勾选后的显示效果，没有提到保存完成状态。按这条要求生成的程序可能只给文字加上删除线，刷新页面后，勾选状态就会丢失。

我们希望用这个功能记住复习进度，目前提出的要求却只涉及显示效果。为了让下次打开页面时还能接着使用，我们需要确定怎样保存勾选状态，以及程序打开时怎样读取记录。如果使用者不小心勾错，还需要允许取消，并保存取消后的状态。

清单中还可能有两项同名内容。使用者勾选其中一项时，程序需要找到这项内容对应的数据。如果只通过标题查找，就无法区分究竟改了哪一项，因此我们需要为条目采用另一种识别方式。

我们首先来确认一下，这次修改想要达到的效果是什么：

  1. 每项内容都可以单独勾选为完成，勾错后可以取消。
  2. 页面能够清楚地区分已完成和待复习的内容。
  3. 在同一浏览器中刷新页面，或者重新打开同一地址时，之前的状态仍然保留。
  4. 两项内容即使标题相同，也能分别勾选、保存和恢复状态。

我们准备让清单在当前设备、当前浏览器中保留复习进度。账号登录、跨设备同步和下次复习时间安排，需要根据后续的使用需要另行讨论。

上面列出的要求，就是这次修改需要满足的需求。我们说明了软件应当怎样工作，也确定了哪些功能暂时不做。接下来才需要考虑用什么办法实现。例如，为了让刷新后的页面还能显示之前的勾选，我们可以使用浏览器提供的 localStorage 保存完成状态，重新打开页面时再读取这些数据。

为了区分同名条目，我们可以给每项内容设置编号。假设两项内容都叫“复习岩石分类”，一项对应课堂笔记，另一项对应练习题，它们就分别使用不同编号。程序保存时按编号记录状态，显示时仍然使用原来的标题。确定条目怎样识别、状态保存在哪里，以及页面打开时怎样读取，属于软件设计的工作。

确定保存办法以后，我们就可以编写代码。使用者勾选或取消条目时，程序根据编号更新对应的完成状态，再将状态写入本地存储。页面重新打开时，程序读取保存的记录，并据此显示复选框。编程助手可以帮助生成这些代码，开发者需要阅读并运行，核对它们是否共同完成了约定行为。

代码写好以后，我们需要实际操作页面。例如，勾选第一项时，其他条目的状态应保持原状。刷新页面以后，第一项应保持已完成。如果取消第一项的勾选后再次刷新，它就应保持未完成。对于同名条目，我们还要分别勾选，核对它们能否保存不同的状态。

你可以先手动完成这些检查。如果以后经常需要重复检查，也可以把其中一些操作写成自动化测试。无论采用哪种方式，我们都需要对照前面的需求，判断实际结果是否符合预期。对于保存与恢复状态的要求，我们需要在勾选后刷新页面，核对原来的状态能否恢复。

如果刷新后勾选消失，我们可以沿着保存与读取的过程排查：勾选事件有没有触发保存，记录是否成功写入，页面重新打开时又读到了什么。代码遗漏了已经确定的保存行为，就需要修复实现。如果我们直到运行时才发现需求中没有讨论保存，就需要与使用者确定应当保留哪些状态，再补充相应代码。

这些操作符合要求以后，我们可以将修改后的网页交给使用者，并说明记录保存在当前浏览器中。使用一段时间后，使用者可能提出：“我希望换一台电脑也能接着复习。”如果准备增加这项功能，我们就需要讨论不同设备怎样访问同一份记录，以及同时修改时怎样保留各自的进度，再据此实现和验证。

完成这项修改，需要从记录复习进度的需要出发，确定功能要求和保存办法。开发者依据这些约定编写代码，并通过实际操作判断结果。网页交给使用者以后，新的使用需要还可能带来后续修改。软件过程讨论的就是这些开发与维护活动怎样安排。

软件过程是开发和维护软件时相互关联的一组活动，以及安排和执行这些活动的方式。例如，开发复习清单时，需要有人确定保存哪些状态，负责实现的开发者才能据此编写保存代码。运行时发现勾选没有保存，又需要回到对应代码排查和修复。活动之间的这种依赖和反馈，是过程的一部分。

如果项目由一位开发者完成，前面的工作都需要这位开发者承担，部分决定可以在编写代码时作出。两位开发者合作时，则需要让负责实现的人知道已经确定的要求。例如，负责需求讨论的开发者希望保存复习进度，负责实现的开发者却只写了勾选与删除线，两人采用了不同理解，得到的程序就无法在刷新以后保留进度。

开发过程中，我们会留下功能要求、代码和运行记录等内容，教材中常把它们称为工作产品或制品。开发者依据功能要求编写代码，再用运行记录说明实际结果。以后有人接手维护，也需要阅读对应版本的代码，查看已有检查步骤。在当前项目中，我们可以用几句话记录功能要求，并写下实际操作与结果，方便后续修改时继续核对。

实际做的事留下的结果接下来怎样使用
确定勾选、取消与保存的要求一份简短的功能约定指导实现，确定要检查哪些结果
决定按编号保存状态条目结构与保存办法让点击、保存和恢复操作使用同一套对应关系
修改页面与数据处理代码差异和可运行的网页阅读修改，运行程序并检查行为
检查勾选、取消和刷新操作步骤、实际结果和问题记录判断是否达到要求，定位需要继续修改的地方

项目与软件过程记录的内容不同。复习清单项目有具体的使用目标、代码和待完成的工作；软件过程说明开发者怎样安排这些工作。两位开发者即使分别独立实现相同功能，也可能采用不同安排。例如，一位在实现前确定主要要求，另一位通过运行初版逐步补充要求。两种安排取得反馈的时间不同，后续需要修改的范围也可能不同。

实际开发中，这些工作可能反复进行。我们可能在选择保存方式时先写一小段代码试验，也可能在检查时重新讨论需求。不同的过程模型会对这些活动作出不同安排，例如把工作划分为几个阶段，或者每次完成一部分功能、检查后再继续开发。后面比较这些模型时，我们就可以具体讨论：每种安排在什么时候有帮助，又可能带来哪些问题。

如果让 AI 参与开发，它也会参与其中的一些工作。你可以让它阅读需求、修改代码、编写测试，但仍然需要检查它是否理解了要求，以及代码和测试是否正确。例如，AI 回复“已完成”以后，你还需要查看实际修改，运行页面，确认勾选能否保存、同名条目是否互相影响。

你可以下载这个复习清单起始项目与提示词，亲手完成上面的修改，也可以先打开页面查看。目前的页面只显示三项复习内容，没有勾选和保存功能，其中两项标题相同、编号不同。项目中的代码都放在一个 HTML 文件里，不需要安装前端框架。下载后，将文件解压到自己的工作目录，通过本地静态服务器打开。

如果你的电脑已经安装 Python，可以在解压目录的终端执行 python -m http.server 8000，再访问 http://localhost:8000，也可以使用编辑器提供的静态预览服务器。检查保存功能时，请使用同一浏览器和同一地址。浏览器按网页来源区分本地存储，来源由协议、主机名和端口组成。例如，http://localhost:8000 和 http://localhost:8001 使用不同的存储，换了端口就可能读不到原来的记录。localStorage 的文档介绍了这种按来源保存的规则。我们通过服务器访问页面，也可以避免直接双击 HTML 文件时，不同浏览器对本地存储处理不一致的问题。如果清除了浏览器数据，保存的记录也可能被删除。

修改前，你可以先运行页面，确认三项内容都能正常显示，再保存一份原始代码。如果你已经会用 Git，可以先提交一次，之后通过差异查看修改。然后，将下面的提示词交给编程助手，让它阅读项目并说明准备怎样实现。你需要先检查它是否理解了勾选、取消、保存，以及同名条目的处理要求。

这条提示词还增加了一个要求：如果保存失败，页面仍然允许勾选和取消，但需要告诉使用者，刚才的操作没有保存。否则，使用者可能以为进度已经记录，下次打开时才发现丢失。你可以阅读 AI 生成的错误处理代码，再模拟保存失败，查看页面是否显示了未保存的提示。使用者需要在操作的页面上看到这项信息。

AI 完成修改以后，你需要阅读代码差异。测试前，让三项内容都保持未完成，再按下面的步骤操作并记录结果：

  1. 勾选课堂笔记对应的“复习岩石分类”，确认练习题对应的同名条目没有被勾选；刷新页面，再次确认两者的状态。
  2. 取消课堂笔记对应条目的勾选，刷新页面，确认它仍然是未完成。
  3. 勾选练习题对应的条目，刷新页面，确认它已完成，而课堂笔记对应的条目仍未完成。
  4. 关闭页面，再在同一浏览器中打开同一地址，确认之前的状态仍然保留。

检查记录中需要写下你做了什么、实际看到了什么。如果结果不符合预期，也把当时的操作记录下来，便于之后复现和排查。

确认正常情况下能够保存以后，你还需要测试写入失败时的行为。请先成功保存一项完成记录，再让编程助手临时模拟写入失败，同时保留正常读取。随后勾选或取消条目，页面应继续响应操作，并提示记录未保存。刷新以后，页面应恢复上一次成功保存的状态。测试结束后，你需要移除临时故障，重新运行正常保存与刷新操作。

如果检查时发现问题，你可以根据操作记录重新运行，排查是代码实现有误，还是前面的要求没有说明清楚。如果某项检查受当前环境限制，无法完成，也请在记录中注明，留待后续确认。

完成这次修改以后，请保留原始代码、修改后的代码、最终确认的功能要求和检查记录。你可以对照这些内容回想：最初要解决什么问题？为此做了哪些工作？每一步用到了什么，又留下了什么？如果遇到问题，你回去修改了哪里？当你能结合自己的开发经历回答这些问题时，也就能具体说明自己采用了怎样的软件过程。

复习与思考

  1. 复选框解决了哪一部分问题？要让清单在下次打开时保留进度，还需要哪些功能，你会怎样验证？
  2. 确定要保存完成状态、选择按编号保存、编写读写代码、检查刷新后的显示，这几件事有什么区别？它们分别产生了哪些供后续使用的结果？
  3. 如果你与另一位开发者合作，哪些要求需要提前告诉对方？请从本节中选出两个容易产生误解的地方。
  4. AI 生成了代码和测试，并回复“全部通过”，你还需要确认什么？如果测试只检查有没有复选框，它遗漏了什么？
  5. 已经约定保存进度，但刷新后记录丢失，与使用者后来提出跨设备同步，有什么不同？这两种情况下，你分别需要重新处理哪些工作？
